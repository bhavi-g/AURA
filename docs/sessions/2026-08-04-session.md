### Pre-existing `poetry.lock` / `pyproject.toml` drift (found this session, not caused by this plan)

`poetry install` does not work on this repo right now, independent of this
branch. Confirmed on **unmodified `main`** (commit `f12ebe3`, before this
branch existed):

```
$ poetry install
Installing dependencies from lock file
pyproject.toml changed significantly since poetry.lock was last generated. Run `poetry lock` to fix the lock file.
```

On **this branch**, `poetry install` fails even earlier, with a different
message, because Task 1 switched `pyproject.toml` to `dynamic = ["version"]`
(no static `[project.version]`), which this environment's Poetry (2.2.1)
rejects outright during config validation, before it even gets to comparing
against the lock file:

```
$ poetry install
The Poetry configuration is invalid:
  - Either [project.version] or [tool.poetry.version] is required in package mode.
```

Both are symptoms of the same root cause: `pyproject.toml` moved to a plain
PEP 621 `[project]` table with a `setuptools`/`setuptools_scm` build backend
some time before this plan started (no `[tool.poetry]` section exists at
all), but `poetry.lock` was never regenerated (or removed) to match, so
Poetry's own consistency checks reject it. This pre-dates this plan — it
reproduces on `main` HEAD `f12ebe3`, prior to any of this branch's commits —
and this branch's dynamic-versioning change just changes *which* Poetry
error surfaces first, it doesn't newly break anything that worked before.

Worked around throughout this plan's execution (Tasks 1-6) the same way
`.github/workflows/ci.yml` already does: `pip install -e ".[dev]"` into a
venv, then run `pytest`/`ruff`/`black`/`isort` directly from that venv,
rather than `poetry install` / `poetry run`. Logged as a new backlog item in
`docs/PROJECT_BRIEF.md` (see below) — not fixed here, out of this phase's
scope.
